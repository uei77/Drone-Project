# ESP32-CAM Setup and First Test Guide

This document explains step by step how to set up and test the ESP32-CAM side of the project on a real board.

> **Scope of this version (v2.2, tiled scan):** The drone searches from 25–30 m. At that height a person is about 1.5 pixels wide in a 96×96 view, so the camera now gives **320×240** and the model looks at **twelve overlapping 96×96 tiles** of each frame, one after the other (one pass = one "sweep"). The same firmware builds for the **AI-Thinker ESP32-CAM** (development, slow sweeps) and for an **ESP32-S3 camera board** (flight target). The model in `model_data.c` is still trained on **synthetic** data: it proves the chain and gives real timing on the board, but it is not fit to fly. The board starts in **SHADOW** mode: it never sends `$EVT`/`$ACT`, only `$SHD`.

This test verifies that:

- The code compiles and flashes to the board
- The camera gives 320×240 gray frames
- The model runs on the board (time per frame, memory)
- The UART link to the flight controller works in both directions

---

## 1. Requirements

### Hardware

| Part | Description |
|---|---|
| ESP32-CAM (AI-Thinker) **or** ESP32-S3 camera board | ESP32-CAM: OV2640, 4 MB PSRAM. ESP32-S3: a board with camera connector and 8 MB PSRAM (pin map in `main/board.h` is for the Freenove ESP32-S3-WROOM CAM / ESP32-S3-EYE layout; another board needs only that block changed) |
| ESP32-CAM-MB programmer board | USB board that plugs under the ESP32-CAM. A USB-TTL (FTDI) adapter also works |
| USB cable | A short, good-quality cable that supports data transfer |
| A second USB-TTL adapter | To play the flight controller on the bench (`training/fake_fc.py`) |

### Software

- ESP-IDF v6.0.x and the VS Code ESP-IDF extension
- Python 3 with `pyserial` for the bench test

## 3. Configuring the ESP32

All settings are in `main/config.h`. For the first test nothing needs to change. The ones you will touch later:

| Setting | Meaning |
|---|---|
| `CAM_MOUNT` | `CAM_MOUNT_DOWN` (camera looks down, image top = nose) or `CAM_MOUNT_FORWARD` |
| `VISION_MODE_DEFAULT` | `VISION_MODE_SHADOW` for first flights; the FC can change it with `$CMD,MODE,n` |
| `COLLECT_MODE` | `1` = data-collection build (Wi-Fi streaming), `0` = flight build |
| `WIFI_SSID`, `WIFI_PASS`, `COLLECT_HOST_IP` | Only for the collect build. Do not write the real values into `config.h` (see below) |
| `LAND_FINAL_ALT_M` | Landing marker: the drone corrects its position while going down to this altitude, then lands |
| `CAM_GROUND_PER_ALT` | Ground length seen along the flight direction per metre of altitude. Measure it for your lens (section 8) |

> **Wi-Fi password:** create `main/wifi_secret.h` with your own three lines (`#define WIFI_SSID "..."`, `#define WIFI_PASS "..."`, `#define COLLECT_HOST_IP "..."`). `config.h` uses that file when it exists, and `.gitignore` keeps it out of git, so the password never reaches GitHub.

## 4. Building

1. In VS Code, open the `esp32_camera_scripts` folder with **File → Open Folder**.
2. Ctrl+Shift+P → **ESP-IDF: Select Current ESP-IDF Version** → choose the installed version.
3. Ctrl+Shift+P → **ESP-IDF: Set Espressif device target** → **esp32** for the ESP32-CAM, **esp32s3** for the S3 board. The target picks the pin map and the board settings.
4. **Delete the old `sdkconfig` file** (the settings in the `sdkconfig.defaults*` files only apply to a fresh `sdkconfig`). Do this again whenever you change the target.
5. Ctrl+Shift+P → **ESP-IDF: Build your project**.

The first build takes several minutes: the camera library, TensorFlow Lite Micro and ESP-NN are downloaded into `managed_components/`.

## 5. Flashing the Board

### 5.1. Connection

**With the ESP32-CAM-MB:** Plug the ESP32-CAM into the MB board (the camera and the USB port on the MB board should face the same direction) and connect the USB cable to the computer. Most MB boards enter flashing mode automatically.

**With a USB-TTL (FTDI) adapter:**

| USB-TTL | ESP32-CAM |
|---|---|
| 5V | 5V |
| GND | GND |
| TX | U0R (GPIO3) |
| RX | U0T (GPIO1) |

Before flashing, **connect IO0 to GND** and press the RST button. When flashing is done, remove the IO0–GND connection and press RST again.

### 5.2. Select the port and flash

1. In Device Manager, look under **Ports (COM & LPT)** to see which COM port the board is using. If it does not appear, install the CH340 (or CP2102) driver.
2. Ctrl+Shift+P → **ESP-IDF: Select Port to Use** → choose that port.
3. Ctrl+Shift+P → **ESP-IDF: Build, Flash and Monitor**.

Press **Ctrl+]** to exit the monitor. If flashing stops with "Failed to connect to ESP32": hold **IO0**, press **RST** once, release IO0, flash again.

## 6. Test Steps

### Test 1: Start-up, camera, model

In the serial monitor you should see:

```
I (...) main: board: AI-Thinker ESP32-CAM, model: selector-v21-synthetic-...
I (...) main: Camera OK: 320x240, 76800 bytes
I (...) infer: ready: arena ..... / 81920 B, 2 image channels, img fast path 1, h in ... out ...
I (...) main: sweep 1200 ms (0.8/s), invoke 98000 us avg, best=marker p=0.04 tile 7, tel age 4294967295 ms
I (...) main: speed 2.0 m/s, limit 2.1 m/s at 15 m          (only once telemetry arrives, Test 3)
```

Write down three numbers from these lines; they are the first real measurements of the model on the board:

- **arena used** (bytes): if it is far below 81920, lower `INFER_ARENA_BYTES` in `infer.cpp` to about used + 8 KB.
- **invoke** (µs per tile): expected about 100 ms on the ESP32-CAM and far less on the ESP32-S3 (not measured yet). If it is much slower, check that the CPU runs at 240 MHz (delete `sdkconfig` and rebuild).
- **sweep** (ms for all 12 tiles): this decides how fast the drone may fly. The ground may move at most half a tile (48 pixels) between two sweeps; then a target is seen about five times while it crosses the frame. At 28 m that is 4.8 m per sweep: 24 m/s with a 0.2 s sweep, 4 m/s with a 1.2 s sweep. The board prints this limit next to the current speed and warns with `TOO FAST` when the drone is above it. Use the measured sweep time for `--gap-ms` when you prepare training data.

`tel age 4294967295` means no telemetry yet; that is expected until Test 3.

### Test 2: Heartbeat without a flight controller

Connect the second adapter's **RX** to **GPIO14** and **GND** to GND, open its COM port at 115200 baud. You should see 5 lines per second:

```
$HB,120,NOTEL,89*..
```

`NOTEL` = the model runs but there is no telemetry, so no decisions are made. `LOST` would mean the model is not running. The last number is sweeps per second × 10.

**Rule for the flight controller:** `LOST` or `NOTEL` never stops the mission. The FC only ignores vision. (Older versions of this guide said the FC should hold on `LOST`; that was wrong: an ESP32 reset would freeze every mission.)

### Test 3: Full link with a fake flight controller

Also connect the adapter's **TX** to **GPIO15**. Then:

```
pip install pyserial
python training/fake_fc.py COM5 --mode 1
```

The script sends `$TEL` at 10 Hz and `$CMD,MODE,1`. Within a second the heartbeat must change to `$HB,...,OK,...` and the monitor's `tel age` must drop below 500 ms. Point the camera at things: in SHADOW mode any would-be event appears as `$SHD,<situation>,<conf>`. With `--mode 2 --ack` the script acts like the real FC script: you will see `$EVT`, then `$ACT`/`$TGT` lines, then `$EVT,<n>,done`.

### Host unit tests (no board)

```
cd test
gcc -std=c11 -Wall -Wextra -I../main test_host.c ../main/proto.c ../main/tracker.c ../main/policy.c ../main/scan.c -lm -o test_host
./test_host
```

Expected: `127 checks, 0 failed`.

## 7. Common Problems

| Symptom | Likely cause | Fix |
|---|---|---|
| `Brownout detector was triggered` and constant rebooting | Insufficient power | Shorter, better USB cable, another USB port. On the drone: separate 5V BEC and a 470–1000 µF capacitor (`warning.txt`) |
| `Camera probe failed` / `camera init failed` | Camera cable not seated, or PSRAM disabled | Reseat the ribbon cable with its latch. Check `CONFIG_SPIRAM=y` |
| `AllocateTensors failed` | Arena too small, or an op missing from the resolver | Raise `INFER_ARENA_BYTES`; compare the op list in `model_meta.h` with `infer_init()` |
| `model tensors do not match model_meta.h` | `model_data.c` and `model_meta.h` come from different exports | Run `export_c.py` again; it writes both |
| `situations.c row N ... != model class ...` | The situation table does not match the model's classes | Edit `situations.c` so the names are in the same order as `MODEL_CLASS_NAMES` |
| invoke much slower than expected | 160 MHz CPU (old `sdkconfig`) | Delete `sdkconfig`, rebuild |
| `no PSRAM for the previous frame` | PSRAM not detected (wrong PSRAM mode for the S3 module) | In `sdkconfig.defaults.esp32s3` switch `CONFIG_SPIRAM_MODE_OCT` to `CONFIG_SPIRAM_MODE_QUAD`, delete `sdkconfig`, rebuild |
| S3: `Camera probe failed` | Pin map does not match the board | Edit the ESP32-S3 block in `main/board.h` |
| `Failed to connect to ESP32` during flashing | Board not in flashing mode | IO0/RST steps at the end of 5.2 |

## 8. Next Steps

1. **Measure on the board** (Test 1) and write the numbers into the architecture document.
2. **Measure the pixel scale:** point the camera straight down from a known height at an object of known length, record it (`COLLECT_MODE 1`, `training/recorder.py`) and count its pixels. Ground per pixel = length ÷ pixels; `CAM_GROUND_PER_ALT` = ground per pixel × 240 ÷ height. Put the value into `config.h` and into `training/tiles.py` (`GROUND_PER_ALT`).
3. **Train a first model on a downloaded dataset:** `training/README.md` (prepare_data → train → evaluate → export_c). `export_c.py` writes `model_data.c`, `model_meta.h` and `situations.c`.
4. **Collect real data:** set `COLLECT_MODE 1`, run `training/recorder.py`, fly. Label the events, add the flights to the training data.
5. **Thermal camera:** a model trained as `v22` has a third image channel for a thermal frame. The firmware side is ready (`thermal.h` describes the frame format, `scan_thermal_tile()` cuts it into tiles) but `thermal.c` has no sensor driver yet: until then the log says `thermal: model wants it, no sensor` and the model runs on the camera alone. The driver needs an ESP32-S3 board (the ESP32-CAM has no free pins).
6. **Flight controller:** the drone will use INAV. `fc/situation_selector.lua` is the ArduPilot reference of the FC side (not usable on INAV); the INAV adapter is not written yet.
7. **Shadow flights**, review every `$SHD`, add false alarms to training as "normal", retrain. Switch to ACTIVE only when shadow flights show ≤ 1 false event per hour.
